The verdict

The hard part is already paid for. The easy part is missing.

UVA has what most programs never get: a ticketing system that records every order, seat, gate scan, transfer and priority-point balance, and a preference centre where fans have already declared their name, their zip, their birthday and which of twelve sports they follow. All of it is collected. All of it is stored. None of it reaches a send.

What is missing is anything that turns a row in that database into a message. Every one of the 78 emails was a manually scheduled broadcast triggered by a calendar date, a game result or an on-sale time. Not one was triggered by something a subscriber did.

The consequence is specific and measurable this week. Scott Stadium has 7,549 unsold seats for Saturday while a campaign called “Sell Out Scott” runs on. The number is published hourly by UVA’s own ticketing API to anyone who asks. The email program has never read it.

The three moves

Ranked by what can ship before the season ends

Days, not weeks

Gameday and digital parking

Parking went digital in June and has not been mentioned in a single email since. Both segments already exist in Paciolan. No new data, no new tooling, one template.

Weeks 1–3

Turn on the fields you collect

First name into the salutation. Sport preference into routing. Zip into drive time. These are Eloqua fields that already hold values.

Weeks 2–6

Win-back and real triggers

Lapsed buyers addressed by the seats they actually sat in, then post-attendance, first-game welcome and a genuine abandoned-gift flow.

Everything here is free and open. No gate, no form, no NDA. A worked trigger binding

The same 600px Eloqua template, entered by a behaviour instead of a calendar date.

# entry
when:      orderhistory.last_order_season in ["F24", "F25"]
          and orderhistory.orders_this_season == 0
          and event.days_until between 3 and 10

# suppression

05 · Getting it into Eloqua

Eloqua can read all of this.
It just needs one thing built first.

Nothing here replaces Eloqua, Paciolan or the agency running the sends. It is a thin layer between two systems that already exist. Below is what Eloqua can natively do, the single dependency that blocks everything personal, the phased build, and a complete field reference for every endpoint.

The one blocker

Eloqua knows an email address. Paciolan knows a patron ID. Nothing joins them.

Every inventory call needs no person identifier at all. Seat counts, sellout percentages, schedules and the donation ladder are per-event, so any email can render them with zero personal data leaving Eloqua.

Every personal call is keyed to a numeric Paciolan patron ID, not an email address. app/ws/patron/{patronId}/myAccount takes it in the path. Order history, memberships and upgrades resolve off the same identity.

So the whole build has exactly one hard dependency: a map from Eloqua contact to Paciolan patron ID. Get that written onto the contact record and every other field follows. Without it, only the inventory half is possible.

Mechanism

Three ways Eloqua takes in outside data

They differ by when the call happens, which is what decides whether a number is fresh. Eloqua never calls Paciolan directly in any of them. There is always a thin service in the middle.

MechanismWhenHow it works Right for
Batch into contact fields and CDOs
Bulk API 2.0
 Nightly A job calls Paciolan, computes per-fan values, imports them to Eloqua. The email then uses plain field merge and dynamic content. No app registration, nothing custom at send time. Seat history, attendance, points, sport affinity, parking status. Six of the eight triggers.
AppCloud Content Service
Registered app
 At send You register a content service with Oracle. When the email is generated, Eloqua calls your endpoint with the contact context and you return HTML that is injected into the send. Calls are signed OAuth 1.0a. Supports a synchronous 200 + text/html response or 204 with async bulk return for large sends. Live inventory and anything that must be current on the day it goes out.
Open-time rendering
Hosted block or image
 On open An image or hosted block pointing at your own endpoint, rendered when the fan opens rather than when Eloqua sends. Not Eloqua-specific; this is how live-content vendors work. Countdowns and seat counts that have to be right on open, not on send.
The inventory case is cheaper than it looks. The seat count is identical for all 100,000 recipients, so it is one call per event, cached, merged into every email. No per-contact call, and no personal data ever leaves the platform. That matters as much for the security review as it does for the engineering.
The build

Four phases, and only the first is a blocker

Phase 0

Identity resolution

Week 1 · blocks everything

Request the Paciolan patron extract, match on email address, and write pac_patron_id back to Eloqua as a contact field. Handle the misses deliberately: shared household emails, alumni with two records, season holders whose tickets sit under a spouse. Expect 70 to 85 percent match on first pass and treat the remainder as a named work item rather than rounding error. Nothing else can start until this field exists.

Phase 1

The nightly pipeline

Weeks 1–2

One scheduled job: pull orders, scans, points and memberships for every mapped patron, flatten them, and import via Bulk API 2.0 into the contact fields and custom data objects below. This alone unlocks win-back, partial-plan, points, parking-gap and sport routing. No Oracle app registration required.

Phase 2

One Cloud Content service

Weeks 2–3

A single registered service that returns the live inventory block: seat count, percentage sold, the per-game table. Cached per event, no personal data in the request. Marketers drag it into any email like a normal content block, which means the team keeps working the way it already works.

Phase 3

Build the triggers

Weeks 3–6

Stand the eight programs up in Eloqua against the new fields, with a shared frequency cap, suppression while a fan is inside a flow, and a 10 percent holdout on every one so the results mean something.

What this unlocks that ticketing alone cannot. A post-game send can name the opponent, both rankings, whether it was a conference game, and link the real box score and recap. A pre-game send can lead with the matchup rather than the price. And it covers all fifteen sports, which is what makes a cross-sport pull on the preference centre’s twelve declared sports actually buildable.
One gap, stated plainly. Final scores are not on this payload. status flips to completed and a box score URL appears, but the score itself lives on the separate wmt.games stats platform, which returned no public JSON on the paths we tried. Treat the score as a dependency to confirm with UVA, not as something already in hand.
One honest caveat about the patron endpoints. What we observed were the fan-facing routes, reached through an ordinary logged-in browser session. Production integration would not replay session calls. It would use Paciolan’s partner integration surface with server credentials, which is the part that is partner-gated and which UVA already has a commercial relationship for. These endpoints prove the data exists and is well structured. They are not the integration path.
06 · Data plan

Paciolan already stores the join key.
It just never leaves the building.

Field-by-field implementation spec. How the identity match works, what every Eloqua field is sourced from, the schema, the sync jobs, and the data-quality traps we found in the live responses that would break a naive build.

The answer to the obvious question

Yes, Paciolan captures email. In five places, and one of them is already a lookup table.

The patron record returns PtrnEvLoginInfoVos, an array of { patronId, email, acctLinkedFl }. That is an email-to-patron-ID map Paciolan already maintains. It is the single most useful object in the whole surface and nothing downstream uses it.

Email also appears as accounts.loginEmail, as primaryContact.emails[] and contacts[].emails[] (each entry carrying value1, value2 and a label, so one contact can hold two addresses), and as patronVo.PtrnEmailVos[].

So the match is feasible, but it is not one to one. The shape is Account → Contacts → multiple emails each, and season tickets frequently sit on one account with a household attached. A plan that assumes one email equals one fan will silently mis-key a meaningful slice of the most valuable segment UVA has.

Step 1

Identity resolution, as a waterfall

Run in order, stop at the first confident hit, and record which tier produced the match so quality can be measured per tier rather than as one blended number.

TierMatch onBehaviour Confidence
1PtrnEvLoginInfoVos.email Direct lookup against Paciolan’s own association between a login email and a patron ID. Respect acctLinkedFl and skip unlinked rows. Authoritative
2accounts.loginEmail Account login. Resolve through primaryContactId to the patron. High
3primaryContact.emails[].value1 / value2 Secondary addresses on the primary contact. Common for alumni who bought with a personal address and subscribed with a work one. High
4contacts[].emails[] Other contacts on the same account. This is the household case. Map to the contact, keep the account ID, and flag is_account_holder = false so the email cannot claim seats that belong to a spouse. Needs a flag

Three collisions to decide before the first run. One email on several contacts, which is a household sharing an address. One contact carrying two addresses in value1 and value2. And an Eloqua contact matching a non-primary contact on an account. Each needs a written rule rather than a best guess, because the wrong call sends somebody else’s seat history to the wrong person.

Step 5

Traps we found in the live responses

Every one of these is real and observed. Each would produce a wrong email rather than an error, which is the expensive kind of bug.

TrapWhat happensRule
The points sentinel priPtsTotal returns a large negative sentinel for an account with no history rather than zero or null. Merge it raw and you tell a fan they have minus seven million points. Reject any negative, coalesce to zero, and suppress the module below a real threshold.
Amounts in cents The donation ladder returns 25000 for $250. Divide by 100 at ingest, never in the template.
Two event timestamps EVENTDT is UTC and EVENTDTFAC is facility-local. For NC State they differ by four hours. Display from FAC, schedule from UTC, and never mix the two.
Kickoff not yet set Unannounced times come back as midnight local, which renders as a real 12:00 AM kickoff. Respect HIDE_TIME and print TBD.
The 12-month history cap maxOrderHistoryMonthRange is 12, so the fan-facing API cannot see a 2024 buyer. That is shorter than the win-back window it would serve. Source order history from the extract, not the account API.
Available versus sellable The seat-availability response carries holdCds separately, so it is not certain that AVAILABLE nets out held inventory. Verify against a box-office number before any send quotes it. Flagged as open rather than assumed.
Booleans that are not isStudent comes back as 0 or 1, and the entitlement flags as strings. Cast explicitly at ingest.
Null versus missing A failed parking sync and a fan with genuinely no pass both look like an empty field. Write a sync timestamp per field group and suppress on stale rather than on empty.
Step 6

Governance

What never moves

No card data, no bank details, no full addresses. Zip is bucketed to a drive-time band at ingest and the raw value is not written. The inventory service carries no personal data in either direction.

Measurement built in

Every contact carries a stable holdout_bucket so a 10 percent control can be held per trigger, and last_triggered_at per flow so a frequency cap can be enforced across teams.

Reversibility

Every synced field is namespaced and every job is idempotent, so the layer can be switched off and the program returns to exactly what it does today. Nothing here is a one-way door.

Sequencing

Which six to build first, and why

  1. Everything you need for Saturday. No new data, deflects support volume on the first weekend of digital parking, and it is the category the preference centre already offers and never uses.
  2. Your parking changed. Same reason, narrower audience, higher urgency.
  3. Real checkout abandon. The creative already exists. Only the trigger is missing.
  4. Section 117 is still open. Highest revenue per send. Proven intent, real seats.
  5. Win, first-time attendee. Converts the single best moment in the season, and today that moment produces one generic blast to everybody.
  6. Add the parking pass. A revenue line and a support-cost line in one send.
The pattern worth noticing. Four of those six need nothing but a segment and a template. The two that need real plumbing, abandon and post-scan, are the two with the largest upside. That is the whole argument for doing the identity work in the data plan first.

Operating rules

How to run it so the numbers mean something

Holdout

10% of every trigger

Withhold a random tenth from each behavioural send. Without it, incrementality is a guess and every win gets attributed to whichever email arrived last.

Governance

A frequency cap across teams

On Aug 19 two emails went out thirteen hours apart from two different teams. A shared cap and a priority order stops that without a meeting.

Suppression

Behaviour beats calendar

Anyone in a triggered flow drops out of the broadcast for its duration. Buyers stop seeing acquisition offers the moment they buy.
